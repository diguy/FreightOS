# 电商物流智能客服产品需求文档

> 项目全局工作规范见 `docs/project/WORKFLOW.md`。新窗口必须与本文件、`ARCD.md`、`project.md` 一起阅读。

## 0. 2026年9月8日产品化基线

本项目当前从“后端智能客服 MVP”进入“消费者端产品化”阶段。第一阶段只面向普通消费者，物流公司服务端放到第二阶段。第一阶段的交付重点是让用户能够通过电脑网页，以自然语言完成物流咨询和受控业务办理。

### 第一阶段必须支持

- 手机号加验证码登录。
- 与智能客服自然语言对话。
- 查询订单物流，支持订单号加自然语言描述。
- 修改收货地址。
- 提交投诉。
- 查询工单号和工单状态。
- 当前对话的多轮记忆，以及最近会话恢复。
- 用户只能访问自己的订单和工单。

### 第一阶段明确不做

- 消费者上传物流规则文档。
- 物流公司后台。
- 实时在线人工客服。
- 完整订单列表、完整工单列表和复杂个人中心。
- 手机端专门适配。

第一阶段交付标准：用户能够登录，像与客服沟通一样完成自然语言对话和物流查询，并在明确确认后安全完成地址修改和投诉工单；客户界面不显示后端 JSON、内部字段名或调试结构。

### 已确认的业务规则

- 第一阶段先支持一家物流公司，例如顺丰。
- 第一阶段先使用系统已有测试订单和物流规则文档。
- 订单修改只允许尚未发货或运输中的订单。
- 地址修改流程必须是“识别订单和新地址、展示待修改内容、用户明确确认、创建工单”。
- 投诉和人工服务必须先收集问题描述和联系方式，再展示提交内容，用户明确确认后创建工单。
- 智能客服无法解决时，先推荐人工工单，用户确认后再创建；不做实时在线转接。
- 物流规则没有明确答案时，可以给出基于知识库的参考判断，但必须明确标注仅供参考，不能把推测说成确定规则。
- 手机号默认脱敏，用户本人可以查看完整信息。

第二阶段再增加物流公司登录、用户和订单管理、工单处理、PDF/Markdown 文档上传、RAGFlow 知识库管理和多公司数据隔离。

### 已确定的前端技术

- `shadcn/ui`：第一阶段消费者端的基础界面组件和蓝白业务系统视觉。
- `assistant-ui`：第一阶段客服聊天窗口、消息展示、输入和会话交互。
- `TanStack Query`：前端与 FastAPI 的请求、缓存、刷新和错误状态管理。

## 1. 产品目标

构建一个可运行、可验证、可扩展的电商物流智能客服产品。当前以后端智能客服 MVP 为基础，进入消费者电脑网页产品化阶段。系统应能理解用户消息，维护多轮会话状态，并在权限和业务条件满足时调用订单、工单或知识库能力。

产品重点不是让大模型直接操作业务数据，而是让 Dify、Python Agent 编排层和业务服务各自承担清晰职责：

- Dify 理解阶段根据当前消息、裁剪后的历史对话、当前槽位和系统提示词，
  输出当前轮结构化意图结果。
- Python Agent 解析、校验、合并会话状态并决定是否允许调用工具。
- 订单和工单服务作为业务事实来源。
- 知识库负责物流规则类问答。
- Redis 保存短期会话状态，MySQL 保存正式业务数据。
- Dify 回答阶段根据当前问题、历史对话、有效会话上下文、工具结果和回答提示词，
  生成客户可见的 `final_answer`。

理解结果和客户回答必须分离。`intent_result`、`tool_result`、槽位和调试字段
只能用于内部编排，不能直接展示给客户。

## 2. MVP 范围

### 2.1 支持的用户能力

1. 查询具体订单的物流位置、运输进度和物流轨迹。
2. 查询运费、时效、禁寄品、签收规则等物流知识。
3. 提交收货地址修改申请。
4. 提交投诉工单。
5. 请求人工客服并创建人工服务工单。
6. 查询已有工单的处理状态。
7. 在信息缺失时只追问必要字段。
8. 在地址修改等写操作执行前要求明确确认。

### 2.2 意图枚举

```text
tracking_query
knowledge_query
address_change
complaint
human_transfer
ticket_status
unknown
```

### 2.3 工具调用安全要求

以下情况不得调用订单、工单或知识库工具：

- 意图为 `unknown`。
- 置信度低于 0.70。
- 必填槽位不完整。
- 当前用户没有通过身份和资源归属校验。
- 地址修改尚未明确确认。
- Dify 输出无法通过结构化校验。

## 3. 业务规则

- 订单和工单只能由归属用户访问。
- 对外错误信息不得泄露其他用户是否拥有某个订单或工单。
- 工单状态使用：
  `pending`、`processing`、`completed`、`rejected`、`cancelled`。
- 工单状态流转必须经过服务层校验。
- 使用 `client_request_id` 保证写入操作幂等。
- Redis 不是订单或工单事实来源。
- 订单、物流轨迹和工单的正式数据以业务数据库为准。

## 4. 当前阶段非目标

第一阶段不包含：

- 真实电商平台或快递平台的生产 API 对接。
- 自动扣款、自动赔付和自动支付。
- 物流公司后台和多公司知识库管理。
- 实时在线人工客服。
- Celery 异步任务和高可用生产部署。
- 让 MCP 绕过会话上下文直接访问数据库。

消费者电脑网页、手机号验证码登录和客户自然语言回答属于第一阶段目标，不再列为非目标。物流公司后台、文档上传和多公司隔离属于第二阶段。

## 5. 验收方向

- Dify 能稳定输出符合契约的结构化结果。
- 意图识别同时使用当前问题、经过裁剪的历史对话、当前槽位和系统提示词。
- 工具执行后，回答阶段同时使用当前问题、历史对话、有效会话上下文、工具结果
  和回答提示词生成自然语言 `final_answer`。
- Python 能正确解析结果并维护跨轮状态。
- 缺槽位、低置信度、越权和未确认写操作都不会误调用工具。
- 订单、知识库、工单和人工转接主链路均有自动化测试。
- MySQL、Redis 和健康检查在真实运行环境中通过验证。
- 即使回答模型超时或输出异常，系统也只能返回安全的确定性兜底话术，
  不得返回 JSON、内部字段名或 Python 字典。
- 每次小切片都有聚焦测试、必要的集成测试和清晰的 Git 版本名。

## 6. 当前验收状态

截至 2026-09-08，MVP 的主要业务能力和 Dify v6 双阶段回答链路已经实现，
并完成核心真实环境验收：

- 默认 MySQL、Redis 环境下项目自身全量测试通过。
- Dify -> FastAPI -> Python Agent -> MySQL 的真实订单查询链路通过。
- RAGFlow 通过 FastAPI 中间层接入，真实知识库评测通过。
- 工单状态查询已覆盖识别、缺槽位、权限、越权、不存在工单和多轮场景。
- MCP 已提供订单查询、工单查询、知识检索、地址修改、投诉和人工转接六项工具。
- 写操作必须经过会话门控、必要槽位和确认校验。
- 当前客户可见回答由 Dify v6 回答阶段输出 `final_answer`，Python 负责校验并保留
  确定性安全兜底；前端不展示内部 JSON、工具结果或调试字段。
- 已修复完成态与待处理任务混淆：已完成且无待处理任务时，未知或模糊消息不得恢复
  已完成业务；存在待处理任务时，未知或模糊消息仍提示缺失信息或要求确认。
