# 项目协作与交付工作流

本文档是本项目的全局协作规范。新窗口开始工作时，应同时阅读：

1. `docs/project/prd.md`：产品目标和需求范围。
2. `docs/project/ARCD.md`：系统架构和模块边界。
3. `docs/project/project.md`：当前阶段、验证事实、难点和下一步。
4. `docs/project/WORKFLOW.md`：本文件，规定每次工作的执行方式。

## 1. 小切片原则

每次只做一个可以独立验证的小切片。

一个小切片应当：

- 有明确的单一目标。
- 有明确的验收标准。
- 只触及完成目标所需的最少文件。
- 可以通过聚焦测试、脚本检查或人工验证判断是否完成。
- 完成后不会留下半完成的跨模块改动。

不在一个切片中同时进行大规模重构、多个业务模块开发、基础设施迁移和文档重写。

## 2. 开始前说明

开始修改前，必须先向用户说明：

- 本次切片的目标。
- 验收标准。
- 准备修改的文件。
- 如果涉及外部服务，说明需要的运行条件和手工验收方式。

如果发现需求存在会改变行为的歧义，先说明采用的解释和假设，再开始编辑。

## 2.1 浏览器操作由用户执行

凡是需要在浏览器或其他图形界面中点击、输入、上传、导入、发布或确认
的操作，AI 不自行操作，必须由用户完成。AI 需要给出可直接执行的精确
步骤，包括：

- 应打开的页面或系统。
- 需要点击的按钮、菜单和选项。
- 需要填写或粘贴的准确文字。
- 需要导入或上传的文件完整路径。
- 预期看到的成功结果。
- 失败时需要反馈的错误文本或截图信息。

AI 可以继续执行代码、命令行、接口调用和自动化测试，但不得替代用户
完成浏览器中的点击、输入、上传、导入、发布或确认动作。用户完成操作
后，应把页面结果、错误信息或截图反馈给 AI，再继续后续分析和处理。

## 3. 实施顺序

每个切片按以下顺序执行：

1. 读取相关代码、测试、契约和当前 Git 状态。
2. 确认本次切片的边界。
3. 修改最少的必要文件。
4. 先运行聚焦测试或最小验证。
5. 根据影响范围运行集成测试或全量测试。
6. 检查差异和提交边界。
7. 只提交本次切片相关文件。
8. 汇报结果、限制和 Git 阶段版本。

当完整回归中只有少量失败时，先完成全部用例并统一归类问题。修正后，
根据失败类型选择少量代表性用例验证修复效果；只有在问题跨越多个模块、
无法按类别隔离，或代表性验证通过后需要确认整体没有回归时，才重新运行
完整回归。不得因为少量失败就默认重复消耗完整外部模型调用额度。

## 4. 测试数据真实性与失败处理

本节是强制执行规则，不是可选建议。凡是涉及订单、工单、物流事件、
用户、会话或其他业务数据的测试，都必须遵守以下要求。

### 4.1 测试前：先对齐真实数据库

1. 先确认当前测试使用的数据库后端、数据库地址、端口和用户身份。
2. 从当前真实数据库查询测试所需的记录，确认测试数据确实存在。
3. 同时确认记录属于本次测试使用的用户，不能只确认编号存在。
4. 测试数据中的订单号、工单号、用户 ID、状态、关联关系和关键字段，
   必须与数据库中的实际值一致。
5. 不得根据历史交接文档、旧报告、示例代码、记忆或猜测，编造数据库
   中不存在的编号或状态。
6. 如果测试数据与数据库不一致，必须在测试开始前修正测试夹具，或者
   明确报告阻塞原因；不得带着未验证的编号直接运行测试。
7. 测试前必须记录数据对齐结果，包括查询时间、数据库环境、使用的用户
   和未找到的记录。历史数据只能作为参考，不能覆盖当前数据库事实。

### 4.2 测试中：单条失败不得中断批量测试

1. 批量测试遇到某一条失败、超时、外部服务错误或断言不通过时，必须
   记录用例 ID、输入、错误类型和错误信息，然后继续执行后续用例。
2. 不得因为前面的用例通过就跳过后面的用例，也不得因为某一条失败就
   提前结束整个批次。
3. 批量测试完成后，统一汇总成功项、失败项、跳过项、缺失输出、无效
   输出和外部依赖错误。
4. 失败结果必须标记为失败或缺失，不能用猜测值、历史结果或人工编造
   的预测填充。
5. 报告指标必须明确说明分母、失败数量和数据是否完整；不完整批次不得
   被描述为“全量通过”。

### 4.3 修复后：按错误类别进行最小复测

1. 如果失败数量较少，先根据根因把失败分组，例如：测试夹具不一致、
   数据权限问题、意图识别错误、实体解析错误、工具门控错误、接口超时
   或数据库连接错误。
2. 修改前必须先说明根因判断、修改目标、验收标准和将修改的文件。
3. 修复后优先选择能够代表该错误类别的少量用例进行复测，不默认重新
   消耗全部外部模型调用或完整批次。
4. 只有在修复影响共享逻辑、跨越多个模块、无法隔离错误类别，或者用户
   明确要求时，才重新运行完整测试集。
5. 少量复测通过，只能证明该错误类别的代表案例已改善；仍需报告尚未
   重新验证的范围和残余风险。

## 5. Git 提交规则

完成验证后，只提交本次切片相关文件。必须保留用户已有的 dirty worktree，不得因为提交方便而把其他改动一起提交。

提交前检查：

```powershell
git status --short
git diff --check
git diff --cached --name-status
```

提交信息和阶段版本名保持一致或高度一致。

## 6. 阶段版本命名

每次提交后必须给出一个可读的阶段版本名，格式为：

```text
主阶段.步骤（本切片名称）
```

例如：

```text
9.2（工单状态查询端到端验收）
```

版本名用于表达当前模块和工作阶段，便于用户进行 Git 回退和分支开发。后续可以基于某个版本派生新路线，例如：

```text
7.2
7.2b
```

当前已完成的上下文基线为：

```text
1.1（项目上下文基线）
```

当前工作流规范切片为：

```text
1.2（项目协作流程规范）
```

## 7. 完成汇报格式

每次切片完成后，至少汇报：

1. 做了什么。
2. 修改了哪些文件。
3. 执行了哪些验证命令以及结果。
4. 尚存的风险或限制。
5. 下一步建议。
6. 阶段版本名和对应 Git 提交。

## 8. 代码和外部系统约束

- 不修改 `vendor/`，除非用户明确要求。
- 不覆盖或删除用户已有改动。
- Dify DSL 修改必须创建新的版本文件，保留旧版本。
- 业务行为变化必须有对应的聚焦测试。
- 外部 Dify、RAGFlow、MySQL、Redis 或 MCP 的 fake 测试不能替代真实环境验收；需要同时记录手工验证步骤。
- `IntentResult` 只表示当前轮结果，跨轮数据放入会话状态。
- Dify 负责当前轮意图识别，Python Agent 负责状态、校验和编排，业务 Service 负责业务事实。
